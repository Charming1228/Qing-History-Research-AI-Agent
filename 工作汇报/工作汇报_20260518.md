### 检索方案（v2）：查询扩展 + 加权BM25 + LLM重排序


#### v2 新增能力

| 模块 | 功能 | 说明 |
|------|------|------|
| **多字段加权BM25** | 题名权重×3, 内容提要×1, 责任者×1 | 标题命中比正文命中得分更高，更符合档案检索直觉 |
| **查询扩展器** (`QingQueryExpander`) | 同义词/下位词/关联词自动补全 | 覆盖地名、军事防务、制度官职、财政、外交通商、洋务工业、灾荒河工、人事、人名别称9大类，100+条扩展映射 |
| **LLM语义重排序** (`LLMReranker`) | BM25粗排Top-20 → LLM精排Top-5 | 解决BM25纯关键词匹配的语义缺失问题，对"台湾防御"类跨领域查询效果显著提升 |

#### 关键技术点

1. **简繁统一** — 档案数据为繁体中文，用户查询为简体。使用OpenCC将索引和查询统一转为简体，同时支持简繁体输入。

2. **清史专有名词词典** — 为jieba添加了40+个清代专有术语，确保官职、制度、人名不被错误切分：
   - 官职：掌印郎中、员外郎、笔帖式、军机大臣、总督、巡抚等
   - 机构：军机处、内务府、理藩院、总理衙门等
   - 制度：八旗、科举、丁忧、引见等
   - 人名：曾国藩、左宗棠、李鸿章、刘铭传等

3. **查询扩展** — 针对清代术语的同义词和关联词，自动扩充查询：
   - 地名扩展：如"台湾"→ 台湾府、基隆、澎湖、淡水等7个下位词
   - 制度扩展：如"赔款"→ 摊赔、赔补、赔缴、分赔、代赔等7个关联词
   - 交叉匹配：用户查询词与清史术语有交集时自动加入该术语

4. **索引缓存** — 首次构建BM25索引后缓存至本地（约300MB），后续启动秒级加载。缓存文件 `.archive_bm25_cache_v2.pkl`。

### 检索系统 v2.1 优化（2026-05-18）

针对实测中发现的问题，对 `archive_search.py` 做了三项代码级优化：

#### 优化1：查询扩展限长限数

**问题**：原扩展器对任意长度的查询无条件添加所有匹配扩展词。如查询"甲午战争后清朝向日本赔款多少"中"赔款"触发了7个扩展词（摊赔/赔补/赔缴/分赔/代赔/赔项/偿还），淹没了"甲午""日本"等关键信号。

**修复**：
- 长查询（>10字）判定为自然语言问题，**跳过扩展**（已有足够关键词）
- 扩展词总数**硬限制为5个**
- 按优先级截断：人名(prio 1) > 地名(prio 2) > 制度/机构(prio 3) > 宽泛类别(prio 4)

#### 优化2：BM25 停用词过滤

**问题**：自然语言问句中"的""是""还是""多少""怎么办"等虚词参与BM25匹配，匹配到大量无关文档。

**修复**：新增50+个中文停用词集合，在 jieba 分词后过滤，不参与 BM25 评分。

#### 优化3：复合词词典扩充

**问题**：jieba 将关键复合词切碎，如"光绪皇帝"→"光绪"+"皇帝"，"慈禧太后"→"慈禧"+"太后"，"北洋水师"→"北洋"+"水师"，导致语义信号稀释。

**修复**：新增 ~20 个清代复合词到 jieba 词典和 `_QING_TERMS`：
- 帝王系列：光绪皇帝、光绪帝、慈禧太后、咸丰皇帝、……、顺治皇帝
- 军事：北洋水师、北洋海军、南洋水师
- 事件/地点：虎门销烟、安庆之战、马关条约、南京条约、瀛台、圆明园、颐和园

## 三、检索方案演进

### 阶段一（v1）：纯BM25
```
用户问题 → 简繁统一 → jieba分词(清史词典) → BM25检索 → Top-5结果
```
局限性：纯关键词匹配，"台湾防御"查询中"台湾"和"防御"各自匹配但语义关联弱。

### 阶段二（v2，当前）：查询扩展 + 加权BM25 + LLM重排序
```
用户问题 → 简繁统一 → 查询扩展(同义词/下位词)
       → jieba分词 → 多字段加权BM25粗排(Top-20)
       → LLM语义重排序(Top-5) → 展示
```
改进效果：
- **查询扩展**：解决清代术语的多样表述问题（如"赔款"→摊赔/赔补/分赔，"煤矿"→煤窑/开矿/矿务）
- **多字段加权**：题名×3权重让标题命中排在正文命中前面
- **LLM重排序**：利用DeepSeek-V4-Pro的语义理解能力，对20条候选精排，弥补BM25的语义缺失

### 阶段三（v2.1，2026-05-18）：扩展控制 + 停用词 + 复合词
针对v2在自然语言问题上的失效，做三项补丁：
- **查询扩展限长限数**：长查询(>10字)跳过扩展，扩展词硬限制5个，按优先级截断
- **BM25停用词过滤**：50+虚词/疑问词不参与匹配
- **复合词词典扩充**：~20个清代复合词加入jieba（"光绪皇帝""北洋水师"等）防止切碎

效果：短关键词查询（乾隆皇帝南巡/光绪帝大婚）Top-5全部精准命中；长自然语言问题因语料自身覆盖限制仍不理想。

## 五、文言 vs 白话档案检索对比系统

### 背景与动机

现有档案检索系统（`archive_search.py`）基于 248K 条内阁大库原始档案，文本均为清代文言文（繁体）。实际使用中，用户以现代白话文输入自然语言问题，存在"问题白话 vs 文档文言"的语义鸿沟。为此，新增 `archive_search_vernacular.py`，构建文言/白话双索引对比检索系统，定量评估白话改写对检索效果的提升幅度。

### 系统架构

```
用户查询（白话）
      │
      ├──→ 文言引擎（248K 原始档案）──→ BM25检索 Top-5 ──┐
      │                                                   ├──→ 并排对比展示
      └──→ 白话引擎（3K LLM改写）  ──→ BM25检索 Top-5 ──┘
```

两个引擎共用同一套 jieba 清史词典、停用词表、OpenCC 简繁转换，保证对比公平性。文言引擎复用 `archive_search.py` 的 `ArchiveSearchEngine`（关闭查询扩展，纯 BM25 对比）；白话引擎为新建的 `VernacularSearchEngine`。

### 白话档案数据

| 项目 | 说明 |
|------|------|
| 数据来源 | `archive_training_data_sample_3000.json`（档案微调数据构建脚本产出） |
| 数据规模 | **3,000条** |
| 数据格式 | LLM 对话格式，`conversations[1].value` 中包含结构化 JSON |
| 核心字段 | `modern_summary`（现代摘要）、`entities_people`（人物）、`entities_office`（机构）、`entities_geo`（地名）、`document_type`（文档类型）、`event_type`（事件类型） |
| 文档构建方式 | 现代摘要 + 人物/机构/地名实体拼接 → jieba分词 → BM25索引 |

每一条白话记录对应一条原始文言档案，由 LLM 将文言内容改写为现代汉语摘要，同时提取结构化实体。这使得白话引擎的文档与用户查询处于同一语义空间。

### 核心实现

#### `VernacularSearchEngine` 类

- **数据加载**：从微调数据 JSON 中解析 `conversations[1].value`（嵌套 JSON 字符串），提取各字段
- **文档文本构建**（`_build_doc_text`）：摘要 + 人名 + 机构名 + 地名拼接，增强实体匹配信号
- **BM25 索引构建**：与文言引擎使用相同的 jieba 词典和停用词表，3000 条规模索引秒级构建完成
- **检索接口**（`search`）：统一简繁转换 → jieba分词 → 停用词过滤 → BM25 打分 → 返回带实体的结构化结果

#### `SearchComparator` 对比器

- 对同一查询分别调用两个引擎，并排展示结果
- 文言结果展示：得分、朝代、年号、题名、内容提要、责任者、责任时间
- 白话结果展示：得分、事件类型、文档类型、现代摘要、人物、地名
- 支持两种运行模式：**交互式查询**（逐条对比）和 **批量测试**（15题自动评测 + 汇总统计）

### 两种运行模式

#### 模式一：交互式对比查询

```bash
python archive_search_vernacular.py
```

- 输入自然语言问题，同时查看文言/白话两边 Top-5 检索结果
- 输入数字编号可快捷选择预设问题
- 输入 `?` 查看预设问题列表
- 输入 `b` 切换到批量测试模式

#### 模式二：批量测试

```bash
python archive_search_vernacular.py --batch
```

- 对 15 道预设问题逐一检索并对比
- 输出每题的白话命中数、白话 Top-1 得分、文言命中数、文言 Top-1 得分
- 最后输出平均命中数和平均得分汇总表

### 15 道批量测试问题

问题设计聚焦 3000 条数据覆盖的主题领域，涵盖官职、财政、刑名、河工、军事、科举、典礼、外交等清代核心政务：

| # | 问题 | 测试维度 |
|---|------|----------|
| 1 | 乾隆年间和珅在朝中担任过哪些官职？ | 人物-官职关联 |
| 2 | 清代地方官员如何向朝廷奏报钱粮征收的完成情况？ | 财政奏销制度 |
| 3 | 乾隆年间直隶地区发生水灾后朝廷如何赈济灾民？ | 灾荒赈济 |
| 4 | 清朝刑部是怎样审理和判决人命案件的？ | 刑名案件 |
| 5 | 清代官员丁忧守制结束后如何重新起复任用？ | 人事制度 |

### 设计考量

1. **公平对比**：文言引擎关闭查询扩展和 LLM 重排序，两边都是纯 BM25，确保对比的是"语料语言差异"而非"管道差异"
2. **规模不对称说明**：文言索引 248K vs 白话索引 3K，直接比较 BM25 分数无意义。重点观察的是返回结果的**主题相关性、信息完整性、可读性**三个维度
3. **可扩展性**：`VernacularSearchEngine` 与 `ArchiveSearchEngine` 接口对齐（均提供 `load_data` / `build_index` / `search`），后续可无缝接入 LLM 重排序和答案生成
4. **微调数据复用**：白话索引直接使用 `档案微调数据构建.py` 产出的 `archive_training_data_sample_3000.json`，无额外数据生产成本

### 代码文件

`archive_search_vernacular.py` — ~360 行，含 `VernacularSearchEngine`、`SearchComparator` 两个核心类，支持交互式/批量两种模式

### 使用方式

```bash
# 交互式对比查询
python archive_search_vernacular.py

# 批量测试（15题自动评测 + 汇总统计）
python archive_search_vernacular.py --batch
```

启动时自动加载文言索引（248K，约30秒）和白话索引（3K，秒级），之后即可反复查询。两个索引均驻留内存，查询响应实时。
